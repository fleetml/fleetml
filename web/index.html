Ship ML models to phones and edge devices in stages, watch how each version behaves, and roll back automatically when one is worse.

FleetML is self-hosted and open source under Apache-2.0, and works with any model file. Android and iOS apps get it through two SDKs, Linux machines through an agent, and the server starts with one docker compose command.

What it does

Rollouts that stop themselves

The end-to-end tests in the repository cover every one of these.

Canary rollouts with a health gate

The gate watches the canary cohort's error rate, and optionally p95 latency, and rolls back or pauses. It looks only at the new version's telemetry from the devices the current stage exposes, so errors from devices outside the cohort never count.

Health gate

Automatic rollback

A rollback, by the gate or by hand, marks the deployment ROLLED_BACK and sends devices back to the previous version, with its URL and sha256. The revert is urgent: devices fetch it on any network, and usually still have it cached as their last-known-good version.

Rollback

Drift detection

PSI on latency, confidence and input features, the last 24 hours against the 7 days before, with an alert on CRITICAL. Every check's PSI is kept, and the Drift page draws it over time.

Tour step 5
  • Rolling rollouts. Batches by device count or percentage at an interval, with the same gate. Strategies
  • Rollback, cancel, one version per model. A manual rollback, also after completion, returns devices to the previous version, and the newest deployment wins. Rollouts
  • A/B experiments. Sticky cohorts, telemetry per arm, a fixed-horizon Welch t-test and a maximum duration. Tour step 4
  • Model registry with integrity checks. Uploads go straight to S3-compatible storage, and the server checks each file's sha256 and size before it can be deployed. Tour step 1
  • Variant selection. Each device gets a build it can run, chosen by OS runtime, RAM and capability score. Tour step 2
  • Artifact signing. Per-project ed25519 signatures, checked on the device before download, with keys that rotate with a grace period. Artifact signing
  • Delta updates. Devices with the previous version download only a delta: 440 KB for a 20 MB model with a retrained head. Delta updates
  • Alerts. Rollback and drift alerts on NATS and to signed webhooks, Slack and email, with retries and a delivery log. Alert sinks
  • Battery and data. Hourly background checks, batched telemetry, and downloads on unmetered networks or while charging unless urgent, all set from the server. Android, iOS
  • Roles and audit log. Viewer, operator and admin roles per project, and an audit log of every change and refused request. Architecture
  • Security. API keys with per-project roles, per-project enrollment keys, revocable device tokens, and devices confined to their project. SECURITY.md
  • Operations. Health probes, Prometheus metrics and a Grafana dashboard, with telemetry delivered at least once and stored once per event ID. Tour step 7
  • Dashboard and CLI. The dashboard runs on a desktop or a phone; the CLI has fleetml push, deploy, experiment, drift, and simulate for a fleet of simulated devices. Tour

How it works

One server, your devices, and a health gate on every staged rollout

Devices heartbeat with the models they run and receive assignments: what to load, update or unload, with presigned download URLs and their experiment arms. Three background loops advance rollouts through the health gate, evaluate experiments and check drift.

Architecture has the request paths, data model, device protocol and trust boundaries; Rollouts has the strategies, the health gate and the statistics.

Is it for you

What it is, and what it is not

A good fit

  • You run models on phones or edge devices and would otherwise build staged rollouts, rollback and drift monitoring yourself.
  • Your apps are Android (minSdk 26) or iOS (15 and later), or your machines run Linux on amd64 or arm64.
  • You keep your runtime: FleetML works with any model file, and your app runs the model with its own runtime.
  • You want it on your infrastructure: you run the server, its Postgres, NATS and object store yourself, with Docker Compose or the Helm chart, so your models and telemetry never leave it.

Not what it is

  • Not an inference runtime: your app or inference process keeps running the model with the runtime you already use.
  • Not a model trainer or converter: it starts from a file you already have, in any format.
  • Not a hosted service, and it does not terminate TLS itself: put its ports behind a TLS proxy before exposing them.
